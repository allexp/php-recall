# План развития PHP Recall

## Хранилище учебных материалов

Цель — перенести документацию из файлов конфигурации и локального кэша в реляционную базу данных и подготовить приложение к добавлению новых типов учебного контента.

### Этап 1. Единая модель материалов

- Добавить категории материалов, например «PHP-функции» и «Концепции разработки».
- Добавить типы материалов: `function` и `concept` с возможностью дальнейшего расширения.
- Для каждого материала хранить отдельными полями:
  - название;
  - уникальный символьный идентификатор (`slug`);
  - определение или сигнатуру;
  - краткое описание;
  - полное описание;
  - формат полного описания;
  - ссылку на источник, если она есть;
  - даты создания и обновления.
- Хранить примеры кода в отдельной связанной таблице, чтобы один материал мог содержать несколько упорядоченных примеров с указанием языка и заголовка.
- Добавить индексы по типу, категории и `slug`, а также ограничение уникальности материала внутри его типа.

### Этап 2. Перенос документации PHP-функций

- Сохранять название функции, сигнатуру, краткое и полное описание в БД.
- Перенести существующий каталог функций из `config/catalog.php`.
- Использовать загрузку PHP Manual для первоначального наполнения и обновления записей, а не как основной источник данных при каждом запросе.
- Предусмотреть повторяемый импорт без создания дублей.

### Этап 3. Концепции разработки

- Добавить в интерфейс самостоятельную категорию «Концепции разработки».
- Поддержать материалы наподобие SOLID, DRY, KISS, шаблонов проектирования и принципов ООП.
- Для SOLID хранить общее определение, краткое описание, полное объяснение и отдельные примеры кода.
- Поддержать подсекции материала, чтобы каждый принцип SOLID можно было раскрывать независимо.

### Этап 4. Управление и поиск

- Добавить административные операции создания, редактирования, публикации и архивирования материалов.
- Добавить поиск по названию, определению и описанию.
- Добавить сортировку и фильтрацию по категории и типу материала.
- Покрыть хранилище, импорт и отображение материалов автоматическими тестами.

## Выбор базы данных

На текущем этапе используется SQLite: она достаточна для одного экземпляра приложения, небольшого числа авторов и умеренного объёма учебных материалов. Структуру таблиц и слой доступа к данным следует делать переносимыми.

Переход на серверную СУБД стоит выполнять при появлении нескольких экземпляров приложения, заметного числа параллельных операций записи или требований к развитому полнотекстовому поиску. Предпочтительный вариант для такого перехода — PostgreSQL. MySQL также подходит, но добавление новых категорий материалов само по себе не является причиной для миграции с SQLite.
